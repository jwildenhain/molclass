Status: Confirmed

Decision date: 2026-08-14

Source: Product-owner interview following the production-readiness assessment and
`PRODUCTION_IMPLEMENTATION_PLAN.md`.

## 1. Purpose and authority

This file records the decisions that implementation must follow. It is the source
of truth when a provisional recommendation in the implementation plan conflicts
with an answer below.

Changes to a confirmed decision must be recorded in this file or superseded by an
Architecture Decision Record. Code, migrations, API contracts, and tests must link
to the applicable decision where behavior would otherwise be ambiguous.

## 3. Binding import behavior

### 3.1 Source and internal identity

1. `mol_id` is an auto-generated internal database key.
2. `source_identifier` is the exact selected SDF value after the documented blank
   validation policy.
3. Source identifiers are unique only in one dataset.
4. Duplicate source identifiers in one dataset fail the affected record.
5. The importer must never suffix, rewrite, or otherwise repair a duplicate
   identifier silently.
6. Identifier punctuation, underscores, slashes, case, and internal whitespace are
   preserved.
7. The identifier property is imported as a selected property as well as stored on
   dataset membership.

Required uniqueness:

```sql
UNIQUE (batch_id, source_identifier)
```

### 3.2 Identifier selection

The analyzer must inspect every valid SDF record. A property is eligible only when:

```text
present_count == total_valid_records
blank_count == 0
distinct_count == total_valid_records
```

Selection order:

1. Exact trimmed property name `Identifiers`.
2. First match in a server-controlled configurable priority list.
3. Deterministic ranking of remaining eligible candidates.
4. Explicit user selection when no unambiguous preferred candidate exists.

The user must confirm the selected identifier even when `Identifiers` is
auto-selected.

### 3.3 Canonical molecule reuse

1. Parse and preserve the original source mol block for audit/export.
2. Run a named and versioned normalization pipeline.
3. Generate the full standard InChI and InChIKey from the normalized structure.
4. Reuse an existing canonical `mol_id` only when the full InChIKey matches and the
   stored normalized identity verifies the match.
5. Preserve dataset-specific identifiers and selected properties independently.
6. Record normalization version and warnings on the import record.
7. When normalization or InChI generation fails, do not merge by name, SMILES, or a
   partial key. Import as an unmerged molecule if its mol block is otherwise valid
   and mark canonicalization status for later repair.

The schema must therefore distinguish:

- Canonical structure associated with `mol_id`.
- Original source record structure associated with the import record or dataset
  membership.
- Dataset-specific source identifier and selected property values.

### 3.4 Property registry and equality

1. Trim surrounding whitespace from a discovered property name.
2. Preserve case and all remaining characters in `original_name`.
3. Match an existing definition by the exact trimmed, case-sensitive name.
4. Generate a safe physical column name on the server.
5. Reuse the same physical column for every exact matching property name.
6. Add one new controlled column when no matching definition exists.
7. Apply all required DDL once under the global import/schema lease before molecule
   insertion begins.
8. Select all properties by default.
9. Import every property not actively unselected by the user.
10. Store missing values as SQL `NULL`, not empty numeric values or zero.

### 3.5 Type inference and widening

Analyze all non-null values before selecting the type. Use this promotion order:

```text
INT -> BIGINT -> DECIMAL(p,s) -> DOUBLE -> CHAR(n)/VARCHAR(n) -> TEXT
```

Rules:

1. Use `CHAR(n)` only when every non-null value has the same bounded length.
2. Use `VARCHAR(n)` for bounded varying text when the projected wide row remains
   within MariaDB limits.
3. Use typed overflow storage for large text, excessive columns, or projected row
   width that is unsafe for the wide table.
4. Preview every new column and widening operation before import confirmation.
5. Widen automatically after confirmation.
6. Reject narrowing, lossy coercion, and truncation.
7. Never accept `sql_type_ddl` or a physical column name from an API request.

### 3.6 Per-record failure and threshold behavior

1. One molecule is one InnoDB transaction.
2. Roll back every domain write for a failed molecule.
3. Persist the molecule failure in a separate short transaction.
4. Continue until the failure ratio exceeds 5 percent or a run-level failure occurs.
5. Calculate the threshold against the analyzer's complete record count.
6. Use integer arithmetic equivalent to
   `failed_records * 20 > total_records` to avoid floating-point boundary errors.
7. When the threshold is crossed, finish the current failure record and submit no
   further molecule work.
8. Mark unprocessed records `NOT_PROCESSED` with
   `FAILURE_THRESHOLD_EXCEEDED`.
9. Retain every successfully committed molecule.
10. Mark the run and dataset `PARTIAL`.
11. Permit model creation only after explicit partial-data acknowledgement.

Run-level failures that stop immediately include database unavailability, schema
failure, exhausted storage, lease loss, cancellation, corrupted upload identity,
and an unrecoverable parser stream failure.

## 4. Binding runtime and security behavior

### 4.1 Local-only deployment

The first release is a single-workstation application.

1. API, frontend, database, worker control, metrics, and RDKit service ports bind to
   loopback unless an internal container network is sufficient.
2. MariaDB must not publish a host port unless a local administration workflow
   requires it.
3. CORS permits only the local frontend origin.
4. Legacy PHP and Perl endpoints receive no route.
5. Remote shell execution remains prohibited even on localhost.
6. Destructive operations still require explicit UI confirmation and audit events.
7. Local service processes run with separate least-privilege database users.
8. File permissions restrict uploads, reports, configuration, and model artifacts to
   the local MolClass account.

The absence of application authentication is conditional. Adding LAN, VPN, reverse
proxy, shared-workstation, cloud, or public access automatically reopens D-09 and
requires authentication and authorization before exposure.

### 4.2 Best-effort recovery

No formal RPO, RTO, availability percentage, clustering, or failover requirement is
part of the first release.

The implementation must still provide:

1. A documented local database backup command.
2. A documented model/artifact backup command.
3. A restore procedure that can be exercised manually.
4. Durable import and model job state across process restarts.
5. No claim of guaranteed recovery or availability in the UI or documentation.

### 4.3 Retention

1. Set source upload retention to 30 days from upload creation.
2. Keep failure reports for 90 days from terminal import state.
3. Keep imported molecule, property, model, and prediction data indefinitely unless
   explicitly deleted.
4. Run cleanup locally on a schedule and record each deletion in an audit event.
5. Do not delete an upload while its analysis or import is active.
6. A retained model manifest must not depend on an expired upload path.

## 5. Model decisions and source evidence

### 5.1 Authoritative model set

The product-owner decision is that all required historical models have already been
rebuilt. The checked-in `spring_boot_predictor/src/main/resources/models_v2`
artifacts are authoritative and must not be retrained as part of production
preparation.

Implementation work for these artifacts is limited to:

1. Inventory every model/header pair.
2. Calculate SHA-256 checksums without modifying bytes.
3. Record model ID, artifact size, checksum, format, and load compatibility.
4. Recover dataset, target, feature, algorithm, and evaluation metadata from the
   database and available reports.
5. Mark unavailable provenance fields as `unknown`; do not invent values.
6. Create immutable manifests and model-card records.
7. Document the complete rebuild procedure if its missing source or execution log
   is recovered.

### 5.2 Repository evidence reviewed

The repository currently demonstrates the following:

| Evidence | Finding |
| --- | --- |
| `spring_boot_predictor/src/main/java/molclass/predictor/PredictionService.java` | Version 2 loads model artifacts from classpath directory `models_v2`. |
| `spring_boot_predictor/src/main/resources/models_v2/` | Contains paired `model_<id>.model` and `header_<id>.obj` artifacts across the current model ID set. |
| `src/molclass/RetrainModels.java` | A separate utility rebuilds only model IDs 4, 20, 21, and 22 and writes them to `models_modern`. |
| `spring_boot_predictor/build.gradle` | Test configuration references `models_modern`, not the complete `models_v2` artifact set. |
| `all_legacy_models_table.md` | Contains model evaluation summaries but is not a build manifest or reproducible build command. |

No checked-in generator, immutable input manifest, or execution record was found
that fully explains creation of every `models_v2` pair. This is a reproducibility
gap, not a request to rebuild the models. D-20 requires documenting the gap and
adding manifests around the existing bytes.

`RetrainModels.java` is not authoritative for `models_v2`. It also contains embedded
database connection details and must not be used as a production rebuild command in
its current form.

### 5.3 Model capabilities

The initial frontend will not assume a fixed algorithm list. Implementation must:

1. Enumerate combinations actually supported by `ModelBuilder`.
2. Add integration tests that build, serialize, load, and predict with each proposed
   combination.
3. Publish only passing combinations through `/api/v1/capabilities/models`.
4. Hide all other options.
5. Keep `models_v2` serving compatibility separate from support for creating new
   models.

## 6. Search decisions

### 6.1 Responsibility split

MariaDB is authoritative for:

- Internal molecule and dataset identity.
- Source identifiers and properties.
- Import/model/prediction state.
- Exact indexed metadata lookup.

RDKit may be authoritative for computed search indexes and chemistry matching used
by:

- Fingerprint similarity candidate generation.
- Exact graph/substructure matching.
- Murcko scaffold generation and membership.
- Chemistry-aware structure normalization where the implementation specification
assigns it that role.

Search results must return MariaDB `mol_id` values and be resolved back through
MariaDB before presentation.

### 6.2 Capacity contract

The reference production capacity is:

```text
Maximum molecules per dataset: 100,000
Maximum molecules in the installation: 1,000,000
```

Performance tests, index design, RDKit index sizing, job chunking, and memory limits
must use this capacity. A higher scale requires a reviewed capacity decision rather
than silent degradation.

## 7. Implementation changes required by these decisions

### 7.1 Database migration updates

The import foundation must be extended to support:

1. Canonical molecule identity and normalization version.
2. Original source structure retention per import record or dataset membership.
3. `NOT_PROCESSED` record state and failure-threshold reason.
4. Partial-data acknowledgement with timestamp and local operator identity.
5. Property overflow definitions and typed overflow values.
6. Upload and report retention timestamps.
7. Model artifact manifest and checksum records.
8. Exact dataset/source uniqueness.

### 7.2 Java analyzer/importer

The Java implementation must include:

1. Complete-file property analysis.
2. `Identifiers` priority and eligibility proof.
3. Exact case-sensitive property registry matching after trim.
4. Safe type inference and widening plans.
5. Streaming record import with internal/source identity separation.
6. Versioned normalization and full InChIKey canonical lookup.
7. Per-record transactions and persisted errors.
8. A strict 5 percent failure cutoff with partial completion.
9. Bounded queues and memory at 100,000 records.

### 7.3 FastAPI and frontend

The API and UI must include:

1. Upload and complete-file analysis.
2. Default-selected properties with explicit opt-out.
3. Identifier proposal, evidence, and confirmation.
4. New/reused/widened/overflow property preview.
5. Queue state, runstep, counters, and 5 percent cutoff display.
6. Partial-data acknowledgement before model creation.
7. Capabilities-driven model configuration.
8. Local-only origins and bindings.

### 7.4 Model artifact work

Do not schedule model retraining. Schedule these tasks instead:

1. Produce a read-only `models_v2` inventory.
2. Generate checksums and pair-validation status.
3. Add manifests without modifying artifacts.
4. Reconcile available metadata.
5. Document missing provenance explicitly.
6. Add compatibility loading tests.

## 8. Accepted risks and constraints

The following risks are accepted for the initial single-workstation release:

| Risk | Accepted constraint or mitigation |
| --- | --- |
| No application authentication | Installation remains local-only and loopback-bound. |
| No formal RPO/RTO/availability | Recovery is best effort, with documented manual backups and durable jobs. |
| Dynamic wide property DDL | One serialized import, property registry, schema lease, preview, and safe widening only. |
| Partial datasets may train models | Stop after more than 5 percent failures and require explicit acknowledgement. |
| Existing model provenance is incomplete | Preserve authoritative bytes, add checksums/manifests, and mark unknown fields. |
| Shared canonical molecules | Preserve original source structures and dataset-specific identifiers/properties. |

## 9. Decision reopen triggers

Reopen the relevant decision before implementation proceeds when any of these occurs:

1. MolClass must be accessed from another workstation.
2. The installation exceeds 100,000 molecules in one dataset or 1,000,000 total.
3. A source identifier must be globally unique.
4. Full InChIKey normalization merges structures that product owners consider
   distinct.
5. MariaDB wide-table limits are reached more often than exceptional overflow.
6. A formal backup, recovery, availability, or regulatory requirement is introduced.
7. New model creation requires an algorithm that fails the capability tests.
8. Recovered rebuild evidence contradicts the checked-in `models_v2` artifact set.
9. The 5 percent cutoff proves inappropriate for a validated scientific workflow.
