# MolClass v3 legacy deprecation map

Date: 2026-08-17

## Purpose

This document maps the tracked legacy Perl and PHP upload/model paths to replacements
that are present in the repository. It also defines the production containment,
rollback prerequisites, and staged removal gates for those paths.

An entry marked as implemented means that replacement code exists. It does not by
itself mean that the replacement has been deployed, secured, load-tested, or accepted
for a particular production environment.

The governing rules are:

1. The v3 database and workers are the only production write path after cutover.
2. Legacy PHP and Perl must never run as a concurrent fallback or dual writer.
3. The legacy database, source uploads, and model artifacts remain immutable migration
   evidence until the retention and reconciliation gates below are complete.
4. Model building does not imply publication. A v3 build remains unavailable until a
   human operator makes an audited approval decision.
5. A legacy behavior with no implemented v3 equivalent is identified as a gap, not
   treated as implicitly replaced.

## Replacement status

The status terms used below are:

- **Implemented**: a v3 replacement is present in this repository.
- **Partial**: only the production-relevant portion is replaced, or user-visible parity
  is not established.
- **No replacement identified**: no equivalent v3 contract is present. The legacy path
  still must not be exposed or allowed to write in production.
- **Reference only**: retain source or immutable data for migration investigation; do
  not route or execute it in production.

## Production disablement policy

### Entry points that must be disabled

The following must be unreachable and non-executable at the first v3 production
cutover:

1. All PHP upload endpoints: `sdf_upload.php`, `sdf_check.php`, `sdf_2moldb.php`, and
   `sdf_chemaxon.php`.
2. All PHP model-creation endpoints: `model_creation.php` through
   `model_creation_4.php`.
3. All Perl upload launchers, analyzers, validators, source rewriters, and conversion
   utilities listed above.
4. All Perl prediction repair scripts listed above.
5. Any web-server rewrite, menu link, cron entry, systemd unit, deployment script, or
   external scheduler that can invoke those paths.
6. Any legacy database account with `INSERT`, `UPDATE`, `DELETE`, `ALTER`, `CREATE`, or
   `DROP` permission used by the PHP/Perl runtime.

Containment means both network and execution controls. Hiding menu links is not
sufficient. The legacy document root must not be publicly routed, scripts must not be
executable by the service account, and legacy database access retained for migration
must use a separate `SELECT`-only account.

### Components retained as read-only migration reference

No legacy entry point is approved as a public production fallback. During migration,
retain the following under restricted operator access:

1. The PHP/Perl source tree, without runtime credentials or execute permission.
2. A consistent read-only dump of the legacy schema and data.
3. Original legacy model BLOBs/files with filenames, byte sizes, and SHA-256 digests.
4. Original SDF uploads and available legacy `.def` files with checksums and provenance.
5. Legacy model, dataset, molecule, property, class, and prediction identifiers needed
   to interpret v3 migration mappings.
6. Historical logs needed to explain failed or partial imports, with secrets removed and
   access restricted.

If an executable legacy read page is temporarily required for reconciliation, it must
be isolated from public traffic, run with a `SELECT`-only legacy account, and have no
shell execution capability. A static export or direct audited SQL query is preferred.

## Data and rollback prerequisites before removal

Legacy runtime files may be removed from a production image only after all of the
following are true. The immutable archive may have a longer retention period.

### Data prerequisites

- A consistent legacy database backup exists, is encrypted, has a recorded SHA-256
  manifest, and has passed a restore test in an isolated environment.
- Legacy model artifacts and BLOBs have been exported or covered by the database backup,
  checksummed, and linked to their legacy model identifiers.
- Required source SDF uploads and legacy analysis files have been inventoried,
  checksummed, and copied to controlled retention storage.
- Every in-scope legacy dataset and model definition has a recorded v3 mapping or an
  explicit, reviewed exclusion reason.
- Dataset reconciliation covers record counts, unique source identifiers, duplicate
  handling, property names/types/values, class labels, failed records, and molecule
  identity mappings.
- Model reconciliation covers definition metadata, feature profile and generation,
  algorithm support, build status, evaluation evidence, artifact hashes, and explicit
  handling of failed or unsupported definitions.
- Prediction data is either reconciled to an approved authoritative path or explicitly
  declared historical-only with an approved retention/export plan.
- All v3 upload, import, feature, and model jobs relevant to cutover are terminal; failed
  records and partial datasets have documented operator decisions.
- A current v3 database and private upload-root backup has passed an isolated restore and
  integrity audit using the migration ledger actually applied in production.

### Operational prerequisites

- Browser acceptance covers upload, analysis, property selection, identifier selection,
  import progress, dataset review, model definition creation, model review, and molecule
  search through only intended v3 endpoints.
- Worker recovery has been exercised for interrupted analysis, import, feature, and model
  jobs without duplicate records or concurrent ownership.
- Production routing, process manifests, cron tables, deployment scripts, and monitoring
  contain no call to a legacy PHP/Perl entry point.
- Access logs show no required legacy traffic for the agreed observation window.
- Operators have a tested v3 backup/restore, queue recovery, model review, and incident
  runbook.
- Security review confirms private upload storage, runtime-injected credentials,
  least-privilege database users, request limits, and no shell interpolation path.
- Owners have approved retention periods for source uploads, legacy data, logs, and model
  artifacts.

### Rollback prerequisites

Rollback must restore one coherent authority; it must never enable legacy and v3 writers
at the same time.

Before cutover, record:

1. The exact v3 database backup, upload-root snapshot, application build, configuration
   version, CDK/Weka versions, and migration ledger used at the cutover boundary.
2. A tested procedure to stop API writes and all v3 workers before restoring the matching
   v3 database and upload-root snapshots.
3. A read-only legacy reference deployment or archive for investigation, not an automatic
   traffic fallback.
4. Named incident authority for deciding whether to restore v3, roll forward, or in an
   exceptional case designate a restored legacy snapshot as the sole writer.
5. A reconciliation procedure for any requests accepted after the cutover snapshot.

Re-enabling legacy writes is a data migration event, not a web-server toggle. It requires
stopping v3 writers, restoring a known-consistent legacy snapshot, recording the authority
change, and later migrating any new legacy writes back into v3. Prefer rollback to the
matching v3 snapshot or a forward fix whenever possible.

## Staged removal checklist

### Stage 0: inventory and freeze

- [ ] Record owners for upload, model build, review, prediction, database, and operations.
- [ ] Freeze new feature work in `html/molclass/web` and the legacy Perl tools.
- [ ] Inventory every route, menu link, cron job, unit, deployment script, database user,
  upload directory, and external caller associated with legacy paths.
- [ ] Capture dependency and checksum manifests for the legacy source, database, SDFs,
  `.def` files, and model artifacts.
- [ ] Record every functionality gap marked Partial or No replacement identified above.

### Stage 1: immediate containment

- [ ] Block public routing to the legacy PHP document root.
- [ ] Disable PHP/Perl script execution and all legacy shell launchers.
- [ ] Remove write privileges from legacy runtime database accounts.
- [ ] Stop and disable legacy cron jobs, background launchers, and repair scripts.
- [ ] Confirm that v3 is the only active upload, import, feature, and model write path.

### Stage 2: replacement acceptance

- [ ] Exercise the complete v3 upload/import workflow with representative and malformed
  SDF files.
- [ ] Confirm identifier auto-selection, property selection, type inference, duplicate
  behavior, per-record failure tracking, restart behavior, and bounded memory usage.
- [ ] Exercise model definition, queued rebuild, read-only review, rejection, and a
  controlled human approval without automatic publication.
- [ ] Resolve or explicitly waive each Partial/No replacement gap required by production.
- [ ] Complete security, capacity, recovery, and operator acceptance.

### Stage 3: data reconciliation and rollback rehearsal

- [ ] Complete dataset, molecule, property, model, artifact, and prediction reconciliation.
- [ ] Record reviewed exceptions for failed, incomplete, or unsupported legacy objects.
- [ ] Run v3 integrity and production audits against the cutover candidate.
- [ ] Restore both legacy reference and v3 backups in isolation and verify their manifests.
- [ ] Rehearse stopping all writers and restoring the coherent v3 database/upload pair.
- [ ] Approve the observation window and objective rollback criteria.

### Stage 4: production cutover

- [ ] Take final consistent legacy and v3 backups and checksum manifests.
- [ ] Stop legacy processes before enabling v3 production writes.
- [ ] Verify legacy URLs fail closed and no legacy database write sessions remain.
- [ ] Start and verify FastAPI, Next.js, Java workers, monitoring, and backups.
- [ ] Confirm that no model was automatically approved or published during cutover.
- [ ] Record the cutover boundary and begin the observation window.

### Stage 5: runtime removal

- [ ] After the observation window, remove legacy PHP/Perl files and dependencies from
  production images and hosts in a separately reviewed change.
- [ ] Remove obsolete web-server rules, service definitions, cron jobs, menu links, upload
  directories, and write-capable database users.
- [ ] Preserve the checksummed, non-executable migration archive under the approved
  retention policy.
- [ ] Update operational documentation and monitoring so legacy endpoints cannot become
  an undocumented fallback.
- [ ] Confirm restore tests and v3 audits still pass after runtime removal.

### Stage 6: archive expiry

- [ ] Obtain data-owner, security, and operational approval before deleting any immutable
  legacy archive.
- [ ] Confirm legal, scientific-reproducibility, and audit retention obligations have
  expired.
- [ ] Preserve permanent metadata and checksums required to explain migrated datasets and
  model provenance.
- [ ] Record archive destruction or transfer in the operational audit log.

## Cutover stop conditions

Stop cutover or removal if any of the following occurs:

- Both legacy and v3 can write concurrently.
- A required legacy dataset, identifier, property, model artifact, or prediction cannot be
  mapped or intentionally excluded.
- Backup restoration or checksum verification fails.
- A v3 import cannot resume safely or creates duplicate dataset records.
- A model is published without an immutable build, complete evidence, artifact validation,
  and a human approval record.
- Production still depends on a legacy URL, cron job, shell launcher, database credential,
  or upload directory.
- Rollback would combine a database snapshot with a mismatched upload-root snapshot.

These conditions require containment and reconciliation. They are not grounds for silently
reactivating a legacy writer.
