# ADR 0007: Legacy ensemble reconciliation

## Status

Accepted

## Evidence

Legacy model definitions 1, 2, and 3 are marked `Ensemble`. Their serialized `model_data` blobs begin with `weka.classifiers.meta.StackingC`, contain J48 base classifiers, and contain `weka.classifiers.functions.LinearRegression` near the serialized meta-classifier graph. A J48 meta-classifier cannot handle the numeric meta-target generated by `StackingC` under Weka 3.8.7 and caused all three production-candidate rebuilds to fail.
Legacy serialized models 5 and 47 independently expose the same recoverable `Ensemble2` graph. It is `StackingC` with 10 folds, seed 1, one execution slot, and a `LinearRegression` meta-classifier. Its ordered base classifiers are J48, Logistic, MultilayerPerceptron, NaiveBayes, OneR, SMO with a degree-1 PolyKernel, and fixed IBk(1) using LinearNNSearch with EuclideanDistance. The retained legacy and current `stackingC.jar` files have identical SHA-256 hashes.

The Weka 3.7.5 artifacts cannot be deserialized directly under Weka 3.8.7 because the serialized `AttributeLocator.m_Attributes` representation changed from `Vector` to `BitSet`. The artifacts therefore establish the graph contract, not binary artifact compatibility or prediction identity.


## Decision

Rebuild `Ensemble` as `StackingC` with J48 and IBk(25) base classifiers and `LinearRegression` as the meta-classifier. Do not substitute this two-base graph for `Ensemble2`.

Implement `Ensemble2` as the exact recovered seven-base `StackingC` graph. Keep fixed IBk(1) inside `Ensemble2`; the adaptive standalone KNN tuning contract does not apply to this component. Both ensemble variants remain inside the v3 common `SpreadSubsample -> SMOTE -> CfsSubsetEval/GreedyStepwise` pipeline. Store each exact resolved graph in its model build manifest.
